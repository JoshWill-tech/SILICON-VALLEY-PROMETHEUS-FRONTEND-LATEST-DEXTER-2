# Prometheus Startup Operating Rules

## Core Rule

Prometheus must be built with startup execution culture.

Move fast, but do not move recklessly.

The team must ship visible progress, protect working systems, preserve premium quality, and avoid wasting time on features that do not improve launch, trust, demo quality, revenue, infrastructure, or system memory.

## Systems Thinking Rule

Before building any feature, ask:

How does this improve the whole system?

Do not judge features in isolation. A feature is only valuable if it improves the grand system:

- user upload flow
- editor experience
- preview generation
- render reliability
- user trust
- creative quality
- backend job flow
- preference memory
- revenue path
- future automation

If a feature looks cool but does not improve the system, delay it.

## Feature Investment Gate

Before building a feature, answer these questions:

1. Does this increase launch speed?
2. Does this increase product trust?
3. Does this improve the demo?
4. Does this improve creative quality?
5. Does this create reusable infrastructure?
6. Does this produce useful data, memory, or user preference signals?
7. Does this help us sell in 7 days?
8. Does this compound over time?
9. Does this reduce future feature drag or operational confusion?
10. Does this remove the current bottleneck?

If a feature does not strongly answer at least 3 of these questions, do not build it yet.

If it does not improve launch speed, demo quality, trust, revenue, or reusable infrastructure, it is probably a distraction.

## Bottleneck Theory Rule

Always identify the current bottleneck before starting new work.

The bottleneck is the one constraint most limiting launch, demo quality, revenue, product trust, or system reliability.

Do not optimize secondary systems while the main bottleneck remains unresolved.

Examples:

- If preview rendering is broken, do not build new templates first.
- If uploads are unreliable, do not build advanced personalization first.
- If users lose progress on refresh, do not add more AI agents first.
- If the demo is not impressive, do not overbuild settings pages.
- If the billing gate blocks editing too early, fix activation before monetization polish.

Every new task must state the bottleneck it solves.

## Power-Law Allocation Rule

Not all work has equal value.

A small number of features will create most of the product value.

Prioritize power-law features:

- reliable upload
- fast transcript generation
- command overlay
- preview generation
- revision feedback loop
- preference memory
- export/paywall moment
- premium motion/template retrieval
- job persistence
- render reliability

Avoid spending serious time on low-leverage features that do not affect activation, trust, demo quality, or revenue.

## Capital Allocation Rule

Engineering time is capital.

Do not spend engineering time casually.

Before making a change, decide whether it is worth the cost.

A feature is worth engineering time only if it improves at least one of:

- launch speed
- demo conversion
- product trust
- creative quality
- system reliability
- reusable infrastructure
- monetization
- user preference learning
- future development speed

If the payoff is unclear, document it as “Later” instead of building it now.

## Fastest Path To Brand Vision Rule

The brand vision is not achieved by building every feature.

The brand vision is achieved by making the core experience feel undeniable.

For Prometheus, the core experience is:

Upload video → provide creative direction → receive premium preview → approve or revise → export.

Anything that improves this loop is high priority.

Anything outside this loop must justify itself.

## System Decision Rule

Every product decision must be classified as one of these:

- Now: required for launch, demo, trust, revenue, or core product flow
- Next: important after the core flow works
- Later: valuable but not urgent
- Not Yet: distracting or too expensive for current stage

Do not build “Later” or “Not Yet” features while “Now” features are broken.

## Time-Casting Rule

Every task must have a time horizon.

Ask:

- Is this needed today?
- Is this needed before demo?
- Is this needed before launch?
- Is this needed after users exist?
- Is this only useful at scale?

If a feature only matters at scale, do not build it before the core demo works.

## Global Product Rule

Prometheus must feel:

- premium
- fast
- reliable
- cinematic
- intelligent
- trustworthy
- commercially serious
